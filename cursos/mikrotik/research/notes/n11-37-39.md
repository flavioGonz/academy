## Cómo cada WAN pone su ruta por defecto
- n:W01. IP fija: la ruta por defecto la escribís vos en /ip/route, distancia 1 por defecto para estáticas.
  - Source: https://manual.mikrotik.com/docs/7.25/user-guides/routing-and-networking-protocols/routing-decision  Quote: "4 As 0.0.0.0/0    10.155.125.1  main                  1"
- n:W02. Cliente DHCP: add-default-route (yes, special-classless, no), default-route-distance (1 por defecto), default-route-tables y, en la 7.25, check-gateway (none, arp, ping, bfd) sobre las rutas que agrega. Con distancias iguales las dos rutas quedan activas y reparten tráfico (ECMP).
  - Source: https://manual.mikrotik.com/docs/7.25/network-management/dhcp/client/  Quote: "When the distances are equal, both routes are active and traffic is shared between them (ECMP)."
  - Source: https://help.mikrotik.com/docs/spaces/ROS/pages/24805500/DHCP  Quote: "check-gateway (none | arp | bgd | ping ; Default: none) Method on how to check route gateway reachability"
- n:W03. Cliente PPPoE: add-default-route y default-route-distance ("sets distance value applied to auto created default route"); use-peer-dns. MTU y MRU hasta 1492.
  - Source: https://help.mikrotik.com/docs/spaces/ROS/pages/2031625/PPPoE  Quote: "default-route-distance ( byte [0..255] ; Default: 1 ) sets distance value applied to auto created default route"
- n:W04. El script de lease del cliente DHCP mantiene una ruta por defecto en otra tabla con el gateway recibido y la borra al perder el lease: sirve para PCC o recursivas con gateway DHCP que cambia.
  - Source: https://manual.mikrotik.com/docs/7.25/network-management/dhcp/client/  Quote: "This example adds a default route to the WAN1 routing table through the received gateway, updates the route when the gateway changes, and removes it when the lease ends."

## distance y check-gateway
- n:W05. Gana la ruta de menor distancia; con distancias iguales, ECMP. check-gateway=ping manda un ping cada 10 s, timeout 1 s, y con dos fallas marca el gateway inalcanzable; en la 7.25 los tiempos se ven en /routing/settings (check-gateway-ping-interval, -timeout, -count).
  - Source: https://manual.mikrotik.com/docs/7.25/user-guides/routing-and-networking-protocols/routing-decision  Quote: "check-gateway-ping-interval: 10s"
- n:W06. check-gateway no se puede usar con un gateway que es una interfaz que no es punto a punto (no hay IP a quién pingear). PPPoE sí es punto a punto.
  - Source: https://manual.mikrotik.com/docs/7.25/user-guides/routing-and-networking-protocols/routing-decision  Quote: "You cannot use the check-gateway parameter on such gateways because no destination IP is known."
- n:W07. Load Balancing (help): failover simple = ruta principal con check-gateway y respaldo con distancia mayor; "check-gateway will make sure the gateway is up". Per-connection es obligatorio cuando controlás una sola punta (router con varias WAN).
  - Source: https://help.mikrotik.com/docs/spaces/ROS/pages/4390920/Load+Balancing  Quote: "This method is mandatory in setups where only one end of the balancing is under our control"
- n:W08. Practicante: check-gateway conmuta en 20 a 30 s y no ve pérdidas parciales; Netwatch con intervalos propios es la alternativa (vende plataforma de gestión).
  - Source: https://mkcontroller.com/blog/tutorials/mikrotik/mikrotik-dual-wan-failover-isp-guide/  Quote: "real switch-over lands around 20 to 30 seconds"
- n:W09. Foro (sindy, 2024): un failover por distancia solo ve caer la conexión al ISP; si el enlace sigue arriba pero el ISP no tiene internet, el router sigue usando la principal.
  - Source: https://forum.mikrotik.com/t/failover-pppoe-static-with-dynamics-gateways/177576  Quote: "if the connection to the ISP stays up but the ISP has some connectivity problems, your router will keep using the primary WAN"

## Rutas recursivas
- n:W10. Failover (WAN Backup): /32 a hosts testigo por el gateway de cada ISP con scope=10; defaults con gateway=testigo, target-scope=11, check-gateway=ping, distancias 1 y 2; masquerade por cada uplink; dos testigos por enlace forman ECMP y la conmutación completa ocurre solo si fallan todos.
  - Source: https://help.mikrotik.com/docs/spaces/ROS/pages/26476608/Failover+WAN+Backup  Quote: "Complete switchover to second link will happen only if all the gateways become unreachable."
- n:W11. scope y target-scope: una ruta solo resuelve su gateway con rutas de scope menor o igual a su target-scope; por defecto la estática tiene scope 30 y target-scope 10.
  - Source: https://manual.mikrotik.com/docs/7.25/user-guides/routing-and-networking-protocols/routing-decision  Quote: "Routes with a scope greater than the maximum accepted value are not used for next-hop lookup."
- n:W12. En RouterOS 7 target-scope y check-gateway se guardan por objeto gateway: cambiar una ruta no afecta a otras que comparten gateway (en la 6 sí).
  - Source: https://help.mikrotik.com/docs/spaces/ROS/pages/30474256/Moving+from+ROSv6+to+v7+with+examples  Quote: "When target-scope or gateway check of a route is changed, ROS v7 will not affect other routes"
- n:W13. Recursiva por PPPoE: en 2015 (RouterOS 6) un usuario no logró resolver la recursiva con la interfaz PPPoE como gateway de la /32 y tuvo que usar la IP del gateway remoto. En 2024 el foro aclara que eso aplica a la 6; en las otras versiones el nombre de la interfaz sirve como gateway y no importa que la IP del gateway cambie.
  - Source: https://forum.mikrotik.com/t/recourse-routing-problem-wont-resolve-route-via-pppoe/88938  Quote: "That is, interface can’t be used here."
  - Source: https://forum.mikrotik.com/t/failover-pppoe-static-with-dynamics-gateways/177576  Quote: "The only case where you need the gateway of the default route via PPPoE to be set to an IP address is when you use the recursive next hop search on RouterOS 6"
- n:W14. Foro 178550 (PPPoE + LTE en 192.168.8.1): el usuario cortaba el cable entre router y módem, lo que no prueba la recursiva; el consejo es cortar la fibra que viene de la pared. Con un solo testigo y ruta /32 por pppoe-out1, al caer el PPPoE el testigo se alcanza por el LTE y Netwatch no ve la caída: hacen falta dos testigos o una ruta blackhole de distancia mayor para el testigo. Usar el DHCP/PPPoE con default propia complica: o add-default-route=no y rutas a mano, o Netwatch.
  - Source: https://forum.mikrotik.com/t/simple-failover-isp1-pppoe-isp2-lte/178550  Quote: "detaching the cable coming from the wall"
  - Source: same  Quote: "add distance=20 dst-address=1.1.1.1/32 type=blackhole"
- n:W15. Foro 178550, caso real de conntrack: al volver la principal, el ping desde la LAN dejó de responder ("Request timed out" cinco veces) hasta borrar las conexiones, porque seguían las conexiones armadas por el LTE. Solución del usuario: Netwatch que borra conexiones en up y down; otro usuario aconseja borrar solo las de timeout largo.
  - Source: https://forum.mikrotik.com/t/simple-failover-isp1-pppoe-isp2-lte/178550  Quote: "When I clear all the firewall connections, I get a response on the primary ISP"
- n:W16. Foro 161606: con dos WAN DHCP (ISP y LTE) el failover solo andaba si caía la interfaz o el módem; la receta que funcionó: testigo con /32 por el ISP más blackhole, Netwatch que cambia default-route-distance del cliente DHCP y borra conexiones ICMP y UDP.
  - Source: https://forum.mikrotik.com/t/automated-wan-failover-using-2-dhcp-wan-connections/161606  Quote: "I found it helps to clear icmp and udp from conntrack."

## NAT y conntrack
- n:W17. Masquerade se pensó para IP dinámica: cuando la interfaz se desconecta o cambia la IP, el router borra las conexiones enmascaradas. Con enlaces inestables puede haber fuga de IPs privadas al volver la principal; la documentación propone una ruta blackhole como alternativa.
  - Source: https://manual.mikrotik.com/docs/7.25/firewall-and-quality-of-service/firewall/nat  Quote: "Every time when the interface disconnects and/or its IP address changes, the router will clear all masqueraded connection tracki"
- n:W18. Failover (WAN Backup) usa una regla de masquerade por interfaz (out-interface=ether1 y ether2); MKController: una regla atada a una sola interfaz rompe la conectividad al conmutar.
  - Source: https://help.mikrotik.com/docs/spaces/ROS/pages/26476608/Failover+WAN+Backup  Quote: "we need to masquerade LAN traffic on both uplinks"
- n:W19. FastTrack saltea firewall y conntrack; las marcas de ruteo distintas de main no se aplican a paquetes con FastTrack ("FastTrack can only work in the main routing table").
  - Source: https://help.mikrotik.com/docs/spaces/ROS/pages/48660587/Mangle  Quote: "Do not apply any other routing marks besides \"main\" for the packets processed by FastTrack"
  - Source: https://help.mikrotik.com/docs/spaces/ROS/pages/130220087/Connection%2Btracking  Quote: "It is up to the administrator to make sure FastTrack does not interfere"

## Acceso entrante con dos WAN
- n:W20. Para que el router responda por la WAN por la que llegó el pedido hacen falta tablas de ruteo y reglas; con servidores en la LAN y dst-nat, marcas de conexión.
  - Source: https://forum.mikrotik.com/t/failover-pppoe-static-with-dynamics-gateways/177576  Quote: "To make the router respond from the address to which the connection request has arrived, you need policy routing"
- n:W21. Foro 143684 (Sob): la marca de ruteo sirve para los paquetes que salen (la respuesta), no para los que entran; se marca la conexión por interfaz de entrada y después la ruta según la marca de conexión; sin eso, un port forward por la segunda WAN responde por la primera.
  - Source: https://forum.mikrotik.com/t/what-is-the-right-way-to-do-port-forward-with-multiple-wans-and-lans/143684  Quote: "Router marks the connection based on incoming interface"
- n:W22. Policy Routing (help): la tabla se crea en /routing/table con fib antes de usarla; dos formas de mandar tráfico a la tabla: mangle o /routing/rule; no mezclar sin saber (mangle tiene prioridad); action=lookup cae a main si la tabla falla, lookup-only-in-table no.
  - Source: https://help.mikrotik.com/docs/spaces/ROS/pages/59965508/Policy+Routing  Quote: "It is not recommended to use both methods at the same time"
- n:W23. Moving v6 a v7: si mangle marca tráfico local, las IP del router dejan de responder; excluir con dst-address-type=!local.
  - Source: https://help.mikrotik.com/docs/spaces/ROS/pages/30474256/Moving+from+ROSv6+to+v7+with+examples  Quote: "be careful not to mark \"local\" traffic"
- n:W24. IP Cloud: el servidor contesta con la dirección desde la que recibió el pedido; el nombre resuelve a public-address con TTL de 60 s; detrás de NAT el router actualiza cada minuto. Back To Home: con IP pública conecta directo, si no, por relay. Con dos WAN el nombre sigue a la WAN por la que sale el router.
  - Source: https://manual.mikrotik.com/docs/7.25/network-management/cloud/  Quote: "The cloud server replies with the address it received the request from"
  - Source: https://manual.mikrotik.com/docs/7.25/network-management/cloud/back-to-home/  Quote: "When the router has a public IP address, the phone connects to it directly. Otherwise, the connection goes through a MikroTik relay server."

## Balanceo PCC
- n:W25. PCC hace un hash de campos del encabezado (direcciones y puertos) y compara el resto con denominador/resto; both-addresses mantiene el par cliente servidor en el mismo enlace. Ejemplo oficial: tablas ISP1_table e ISP2_table, accept a las redes conectadas, marcas de conexión para lo que entra por cada ISP (input) y PCC para lo nuevo de la LAN, mark-routing en prerouting y output, una default con check-gateway por tabla y defaults en main con distancias 1 y 2 para el failover, masquerade por interfaz. PCC no sirve con Hotspot.
  - Source: https://help.mikrotik.com/docs/spaces/ROS/pages/152600617/Per+connection+classifier  Quote: "replies must leave via same interface (from same Public IP) request came"
  - Source: same  Quote: "PCC is not a valid method, in case of Hotspot"
